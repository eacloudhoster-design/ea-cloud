# Private provisioning release candidate — no deployment authorization

## Implemented and tested here

`private-service.cjs` is an executable HTTP service source, not an installed/running service. Loopback only at a configured port 10000–11000; strong constant-time bearer, strict body schema/size and demo/role restrictions, no caller commands/paths, default disabled. Root-private durable intent precedes one hash-pinned driver invocation; same-request changed credentials conflict, completed requests replay metadata only, incomplete requests hold with no retry. Passwords go only through driver stdin, never argv/environment/files/logs; stdout/stderr discarded. Timeout kills the new driver process group, retaining intent for reconciliation. HMAC payload binding stores no reversible credential. Existing mandatory stop files must be present; provisioning never clears them. This condition is provisioning-only, never a trading permission gate.

`mt5-provisioning-port.ts` implements the existing DedicatedWorkerPort against this exact authenticated /v1/provision API. Separate URL/token from status gateway; HTTPS except loopback, no embedded credentials, no redirects, bounded AbortSignal. A `worker_prepared` response is NOT account authentication. Existing queue consumer independently requires actual readBoundAccount proof with exact demo/role/broker and execution disabled/read-only, rechecks owner authorization, then erases queued ciphertext and reports awaiting_verification. Final owner binding still uses the existing user Connect form.

`mt5-provisioning-runtime.ts` adds serial polling/expiry to API lifecycle only when BOTH MT5_SELF_SERVICE_PROVISIONING=1 and MT5_PROVISIONING_CONSUMER=1. Default off; startup config failure skips consumer without blocking API. Shutdown stops future polling; an in-flight request remains subject to its existing bound and uncertainty journal, never requeued. UI polls queued/provisioning status at five seconds only while not submitting, stops on unmount/terminal state, and does not show broker success from a queue status.

New targeted tests: test-private-provisioner.cjs 12 assertions PASS, test-provisioner-port.cjs 7 assertions PASS; four changed TypeScript components syntax/transpile PASS, git diff --check PASS. All injected fake driver/HTTP; no network listener, subprocess, database, worker creation or broker call. Previous passing suites not repeated. No full build, SQL migration or deployed acceptance claim.

## Exact missing host integration

A reviewed immutable executable **dedicated-worker-driver is NOT supplied** because current infrastructure has no verified generic user-worker creation interface. Do not install a fake driver that merely exits zero. It must implement one request-bound, idempotent allocation of separate account user/home/Wine prefix/terminal data, using verified official existing templates/installers; enforce ownership and capacity; securely provision encrypted/private credentials; refuse live identities; keep AutoTrading/execution disabled; coordinate exclusive prefix ownership; start only approved read-only adapter units; register the exact account in the private status registry; verify identity/role; audit and reconcile partial setup. It receives one JSON payload over stdin, must not log it or return secrets, and exits zero only after that setup is verified. Backend still independently checks the SDK proof.

Driver must be root-owned, non-group/world-writable, regular non-symlink, at a fixed reviewed release path with matching SHA256. Parent path ownership/mount/TOCTOU hardening, service sandbox policy, least-privilege helper split and immutable release attestation require security review before installation. This wrapper currently trusts root-controlled deployment paths; it is not a fully isolated root executor. Existing service templates/adapters must not be overwritten by a generic installer. SDK/Wine ABI/runtime/controller acceptance remains required before real provisioning is operational.

## Rollback/recovery

Disable consumer flag first, then request-submission flag through approved deployment. Stop only newly approved service; preserve all root intent files, queue/audit rows and uncertain worker allocations. Expiry/cancellation erases queued encrypted credentials only where safe; never remove active credentials or unknown workers automatically. Return app/backend code to prior reviewed release without down-migrating shared tables, changing original secrets, replacing accounts or clearing emergency stops. Retain new additive tables while unresolved jobs exist. Reconcile partial host setup manually with request ID before reattempt. No terminal rebuild, generic database restore, reboot or hosting migration is part of rollback.

Both stops and execution-disabled state preserved. Actual worker creation/authentication and broker-copy latency remain unverified. This is service/queue/application wiring ready for code review, NOT end-to-end provisioning readiness.
