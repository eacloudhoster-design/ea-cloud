# Application-side MT5 onboarding

Connect now verifies an assigned account or, only after ACCOUNT_NOT_ASSIGNED and explicit ownership consent, queues the existing encrypted provisioning request. This requires both existing provisioning/consumer gates. HTTP202 means pending, never connected. The client polls GET status, never retries account-creation POSTs automatically, and accepts completion only after a fresh exact-account engine status proof.

After the existing private provisioner supplies a read-only worker and a fresh broker identity proof, the consumer rechecks licence/ownership and binds the account through the existing guarded application transaction. Raw pg rows are normalized to the shared licence DTO. Copying is paused. Secrets are erased from completed queue records. Incomplete/uncertain jobs remain held and are never automatically replayed. Duplicate pending/held/completed assignments for the same owned account cannot create another request under a new key.

The broader integration branch has a separate nullable rawPayload correction. This minimal main-based release retains its existing execution source unchanged; the affected newer risk-sizing code is not part of this release. Person2 engine, Wine, VPS, terminal, journals and safety controls are unchanged by this application patch.

Runtime prerequisites remain the existing MT5_SELF_SERVICE_PROVISIONING=1, MT5_PROVISIONING_CONSUMER=1, private MT5_PROVISIONER_URL/TOKEN, status gateway credentials and a provisioner with approved capacity. No credential, endpoint, assignment, flag or VPS service is invented or changed here. Provisioning can initialize a broker session and must only be enabled for authorized onboarding. Existing gates remain unchanged unless verified configuration is separately available.

Validation uses the existing session/PGlite and provisioning fixtures with intercepted SDK gateway/provisioner responses. These checks do not prove real broker onboarding, mobile production startup or provider deployment.
