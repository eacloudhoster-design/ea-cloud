## Implemented in source

Both client MT5 tab and mentor connection page embed shared lib/mt5-ui/ProvisioningRequestForm.tsx. A client can select only follower; mentor only master. Backend enforces the authenticated role, ignoring caller IDs. Broker selection supports five profiles; exact login/server and password submitted by same-origin cookie-authenticated POST. Password is cleared from React state at submission, never placed in storage/URL/logs or returned by status APIs. This is DEMO-only. Selecting a master/follower purpose does not assign a mentor, change allocation or enable copying.

POST/GET /api/app/mt5-provisioning/requests and /api/admin/mt5-provisioning/requests plus POST /:id/cancel use existing session/portal authentication and origin protection. Proxy allowlist includes these exact management paths. Status/list/cancel are owner-scoped. Only queued requests are cancellable; an in-flight worker cannot be assumed safely cancelled. Both connected and awaiting-verification jobs require fresh connection confirmation for UI purposes; stored job success alone never displays Connected. Existing connect forms and SDK proof routes remain the account-binding step.

Server validates exact schema, UUID request key, supported broker, safe login, exact server, role/demo and password bounds. Uses existing AES-GCM MT5 credential encryption with unchanged SESSION_SECRET. HMAC request digest includes owner and credential input for idempotency, without persisting plaintext. Same-owner advisory lock serializes retries/quota; changed payload with same key conflicts; one unresolved request/owner prevents unbounded creation. Expired queued rows erase ciphertext when next owner submission is processed; explicit expireQueuedProvisioning maintenance hook also exists but no timer is installed. API projections contain only selected public metadata and fixed error codes, never ciphertext/raw vendor errors.

Reviewed additive migration migrations/20261111_mt5_provisioning_requests.sql creates one queue table/indexes only; NOT APPLIED. Does not alter earlier migration or original records. New POST/status endpoints are disabled unless MT5_SELF_SERVICE_PROVISIONING=1. Default capabilities explicitly advertise selfServiceProvisioning=false because automatic worker creation is not available. requestSubmissionAvailable only advertises the deployment flag, not engine connectivity. The UI can request/refresh and reports configuration unavailable when disabled. Existing verified account connect path remains usable without new table while feature off.

Inactive processNextProvisioning(port) contract claims queued row with FOR UPDATE SKIP LOCKED and persists provisioning BEFORE dispatch. Only caller-provided private DedicatedWorkerPort can create an actual dedicated worker; no such network/API implementation is invented or installed. Timeout/exception/partial setup becomes review_required; no automatic retry or requeue of crashed/in-flight jobs. A crash can leave encrypted row in provisioning; approved recovery/retention tooling must inspect and securely retire it, never auto-retry. Deadline/AbortSignal does not prove worker operation cancelled. Port must independently enforce one request/worker, lease ownership, root stop gates and reconciliation.

After port completion, existing readBoundAccount verifies actual exact login/server/demo/role/broker with execution disabled/read_only=true. Only then state becomes awaiting_verification, with queued ciphertext erased. User re-enters account password into existing Connect form for proof and encrypted owner binding; markProvisioningBound updates matching awaiting job after that binding. Provisioning job status update failure cannot undo existing successful connection; fixed warning reports possible stale job metadata. No password ever returned to UI. A stored connected job still is not fresh connectivity.
